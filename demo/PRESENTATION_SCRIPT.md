## SCN 01 · 문제 정의 `00:00 – 01:30` · 판넬 앞

**무대 지시**
- 판넬 섹션 1 "문제 정의" 가리키며 시작
- 25%/75% 파이차트 부분에서 잠깐 멈추기
- 기존 LSTM vs Self-Healing 비교표 가리키며 마무리

**대사**

개발자는 매주 **17.3시간**을 장애 분석과 디버깅에 씁니다. 코드를 짜는 시간보다 더 많습니다.

Prometheus, Grafana 같은 기존 모니터링 도구는 **탐지만** 합니다. 어디서 뭔가 터졌다는 알림을 보내는 건 잘 하는데 — 원인 분석, 복구 명령 생성, 실제 실행, 이 세 단계는 결국 사람이 합니다. OOM이든, 디스크 풀이든, DB 타임아웃이든, 매번 사람이 뛰어야 합니다.

저희가 만든 건 이 과정 전체를 자동화하는 **Self-Healing MLOps Agent**입니다. 기존 LSTM 방식과의 차이는 바로 여기 — **RAG 기반 유사 사례 검색**으로 이미 알고 있는 장애는 즉시 복구하고, 처음 보는 장애는 LLM이 새 명령을 만들어냅니다.

## SCN 02 · 시스템 구조 `01:30 – 02:30` · 판넬 앞

**무대 지시**
- 판넬 섹션 5 "시스템 구성도" 앞으로 이동
- 1번 박스부터 8번까지 순서대로 손가락으로 짚으며
- YES/NO 분기 화살표 강조

**대사**

흐름은 이렇습니다. **로그 수집** → **전처리**, 여기서 Debouncer와 CircuitBreaker가 중복 로그를 걸러냅니다 — 중복 로그를 **95% 감소**시켰습니다.

그 다음 RAG가 Vector DB에서 유사 사례를 검색합니다. **유사 사례가 있으면** — L1 경로 — 기존 복구 정책을 바로 적용합니다. **없으면** — L2 경로 — Qwen LLM이 새 복구 명령을 생성합니다.

그 명령이 보안 검증을 통과하면 실행하고, 결과를 Vector DB에 업데이트해서 다음번엔 더 잘 대응합니다. 실행 전 보안 검증이 반드시 들어갑니다.

## SCN 03 · 데모 1 — OOM (L1 캐시 경로) `02:30 – 04:15` · 터미널

**무대 지시**
- 에이전트 터미널(A) 화면으로 전환
- 장애 주입기 터미널(B)에서 실행:
  ```bash
  python3 demo/inject_failure.py --type oom
  ```
- Enter 누르고 → 터미널 A로 시선 유도
- "메모리 최적화 완료" 출력 나오면 포인트

> **주의:** 에이전트가 반응하는 데 2~5초 걸립니다. 침묵이 어색하면 아래 괄호 대사로 채우세요.

**대사**

지금 이 터미널에서 에이전트가 실시간으로 로그 파일을 감시하고 있습니다. 여기에 OOM 장애를 주입하겠습니다.

*(inject 실행 후)* 보시면 CRITICAL 로그가 파일에 써지고 — 에이전트가 감지합니다. RAG로 Vector DB를 검색해서 OOM 유사 사례를 찾아냅니다.

*(반응 기다리는 중)* L1 캐시 히트입니다. 기존 복구 정책을 재사용해서 — 지금 보시는 것처럼 — **메모리 최적화 명령을 실행**했습니다. 응답시간 약 **30ms**입니다. 사람이 직접 처리하면 최소 수십 분인 작업이 30ms에 끝났습니다.

## SCN 04 · 데모 2 — DB 타임아웃 + L2 경로 설명 `04:15 – 05:30` · 터미널

**무대 지시**
- 장애 주입기 터미널(B)에서 실행:
  ```bash
  python3 demo/inject_failure.py --type db_timeout
  ```
- 에이전트 반응 확인 후 판넬 섹션 5 YES/NO 분기 가리키기
- 판넬 섹션 6 핵심 기술 표의 "LLM 기반 복구 생성" 행 포인트

**대사**

이번엔 DB 커넥션 풀 고갈입니다. 주입하겠습니다.

방금 OOM과 달리, 만약 이 장애 패턴이 Vector DB에 없거나 유사도가 threshold **τ=0.6** 아래로 나오면 L2 경로로 넘어갑니다. Qwen **2.5-3B-Instruct** 로컬 LLM이 로그를 분석하고 복구 명령을 생성합니다.

이 경우 응답시간은 약 **3~4초**로 느려지지만 — 사람이 온콜 받고 로그 열고 원인 파악하는 **30분**에 비하면 압도적으로 빠릅니다. 그리고 이 결과는 Vector DB에 저장되기 때문에, 다음번 같은 장애는 **L1 경로로 30ms**에 처리됩니다. 시스템이 학습합니다.

## SCN 05 · 실험 결과 `05:30 – 06:30` · 대시보드 + 판넬

**무대 지시**
- 브라우저 대시보드로 전환 (미리 열어둘 것)
- L1 Hit Rate, 응답시간, 성공률 화면에서 직접 가리키기
- 판넬 섹션 8 "성능 검증" 표로 이동해서 마무리

**대사**

실험 결과를 보면 — 대시보드에서 실시간으로 확인하실 수 있는데 — **L1 Hit Rate 98.8%**입니다. 99%에 가까운 케이스가 LLM을 거치지 않고 캐시에서 바로 처리됩니다.

τ와 Top-K를 어떻게 결정했는지 말씀드리면 — threshold를 0.1부터 1.5까지 sweep해봤을 때, **τ=0.6**에서 F1이 0.815로 최고였고, Top-K는 1에서 5로 늘렸을 때 Unknown 케이스가 **184건 → 5건**으로 줄었습니다. 이 두 파라미터를 실험으로 확정했습니다.

보안 측면에서는 rm -rf 계열 위험 명령 **30종**을 모두 차단했고, 차단율 **100%**입니다. 그리고 지속 학습 효과 — 데이터셋 50건일 때 Accuracy **0.054**에서 1,016건이 됐을 때 **0.378**로, 사례가 쌓일수록 시스템이 더 정확해집니다.

## SCN 06 · 마무리 `06:30 – 07:00` · 판넬 앞

**무대 지시**
- 판넬 전체 앞으로 한 발짝 뒤로 물러서서
- 마지막 문장에서 심사위원과 눈 맞추기

**대사**

정리하면, 저희 에이전트는 **98.8%의 장애를 평균 30ms**에 자동 처리하고, 나머지는 LLM이 새 복구 명령을 만들어냅니다. 악성 명령 차단과 사람 승인 체계로 안전성도 확보했습니다.

반복 장애로 인한 운영 비용 절감, AI 서비스 운영 기업 대상 **B2B Self-Healing 솔루션**으로 확장할 수 있습니다. 이상입니다. 감사합니다.

## 예상 Q&A

| 질문 | 답변 |
|---|---|
| 실제 Kubernetes에서 돌아가나요? | 현재 로컬 시뮬레이션이며, `executor.py`에 K8s API 연동 코드 구현 완료. 설정만 바꾸면 됩니다. |
| LLM이 잘못된 명령을 내리면? | 보안 검증이 실행 전에 차단. 위험 명령 30종 100% 차단, 나머지는 ESCALATE_TO_HUMAN. |
| RAG DB는 어디서 구축했나요? | GitHub API, LogHub, 공식 레포지토리에서 수집, 10개 카테고리 1,016건 ChromaDB에 저장. |
| LLM 비용 문제는? | L1 캐시가 98.8% 처리, LLM은 1.2%만 호출. Qwen 2.5 로컬 실행으로 API 비용 없음. |
| τ=0.6은 왜 그 값인가요? | 0.1~1.5 sweep 실험에서 τ=0.6일 때 F1=0.815 최고. 그 이상은 오분류 증가. |
| 데모가 항상 성공하나요? | AUTO_APPROVE 모드라 승인 대기 없음. 에이전트 반응까지 2~5초 지연은 정상. |
