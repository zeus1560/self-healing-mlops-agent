# 자체 로그 누적 설계 (데이터 증설 준비)

이 문서는 코드가 아니라 **설계 문서**다. "LogHub 외부 로그만으로는 학습 데이터
확장에 부족하다"는 문제를 어떻게 풀지 — 수집 동의와 익명화 방식 중심으로 —
미리 정리해두고, 실제 수집 코드는 착수하지 않는다.

## 1. 왜 필요한가

현재 ChromaDB L1 캐시에 쌓인 데이터(총 1,318건, [README](../README.md#훈련-데이터-파이프라인-chromadb-총-1318건-실측-2026-09-18) 참고)는 세 갈래다.

| 소스 | 성격 | 한계 |
|---|---|---|
| GitHub 이슈 크롤링 (`source` 없음, 308건) | 공개 이슈 트래커의 에러 스니펫 | 우리 배포 환경의 실제 에러 분포와 무관 |
| 카오스 인젝터 시그니처 | 인위적으로 주입한 장애 패턴 | 커버리지가 우리가 미리 상상한 실패 케이스로 제한됨 |
| `source="online_learning"` (런타임 자동학습, `src/llm_engine.py:1327` `learn_from_feedback`) | L2/Rule이 실제로 성공시킨 (에러→커맨드) 쌍 | **이미 코드로 존재** — 배포된 만큼만, 우연히 마주친 에러만 쌓임 |

LogHub 로그(10개 무관 시스템, 2만 줄)는 오탐률(FP) **검증용**으로만 쓰고
있고([README](../README.md) FP 실측 섹션 참고), 애초에 우리 타깃 앱과 무관한
일반 시스템 로그라 학습 데이터 확장 소스로 쓰기엔 맞지 않다 — 이 부분은
최종 발표 포맷이 뭐로 정해지든 공통으로 지적되는 문제라, 포맷이 확정되기
전에 "우리 자체 로그를 어떻게 누적할지"만 먼저 설계해둔다.

## 2. 무엇을 수집하나 (범위)

- **대상**: `src/log_watcher.py`가 감시하는 타깃 앱/운영 서버의 에러 로그
  원문(`error_log`), 파이프라인이 생성한 커맨드·reasoning, 실행 성공/실패
  결과. 새 데이터 종류를 만드는 게 아니라 `learn_from_feedback`이 이미
  만드는 것과 같은 종류의 데이터를, **일회성 온라인 학습(upsert)에 그치지
  않고 재사용 가능한 데이터셋(export 가능한 형태)으로 별도 누적**하는 절차를
  설계하는 것.
- **환경**: 실사용자 트래픽이 있는 실서비스가 아니라 팀이 운영하는
  데모/타깃 앱(클라우드 VM)이라 일반 사용자 개인정보가
  섞일 가능성은 낮다. 다만 로그 원문에는 파일 경로(`/home/<user>/...`),
  호스트명, 내부 IP, 환경변수 값 등 운영 환경 식별 정보가 그대로 노출될 수
  있다 — 이게 아래 익명화 절차가 필요한 이유.
- **스코프 밖**: 학교 서버나 외부 파트너 등 진짜 제3자 서비스에 붙이는
  경우는 별도 동의·계약 검토가 필요한 완전히 다른 문제라 이번 설계에서는
  다루지 않는다.

## 3. 수집 동의

"동의"의 대상은 최종 사용자가 아니라 **로그가 나오는 서버를 실제로 운영·
사용하는 사람**(팀원, 공동 운영자, 추후 시연 협조자)이다.

- **원칙**: opt-in. 로그 수집이 켜지기 *전에* 어떤 데이터가(§2 범위), 어떤
  목적으로(모델 재학습용 데이터셋 축적), 어디에 저장되는지(ChromaDB +
  raw 로그 파일, 클라우드 VM 로컬) 고지한다.
- **문서화**: 동의 여부를 코드 설정값이 아니라 사람이 읽는 기록으로 남긴다
  — 이 저장소에 `CONSENT.md` 또는 이 문서 하단에 "누가/언제/무엇에 동의"
  표를 추가하는 방식을 제안(아직 미작성, 실제 시연 협조자가 정해지면 채움).
- **철회**: 동의 철회 시 그 시점 이후 수집 중단 + 이미 쌓인 데이터 중 해당
  소스에서 온 것 식별·삭제가 가능해야 한다. 현재 `learned_*` doc_id는
  에러 텍스트의 MD5 해시라 소스별로 구분되지 않는다 — 나중에 코드화할 때
  metadata에 "수집 동의 세션 ID" 같은 필드를 추가해야 삭제가 가능해진다는
  점만 여기 남겨둔다(§6 TODO).

## 4. 익명화 방식

핵심 전제: 지금 구조(`learn_from_feedback`)는 에러 로그 **원문을 그대로**
ChromaDB `documents`에 저장한다. MD5 해시(`doc_id`)는 중복 제거용 ID일 뿐
원문 자체를 비식별화하지 않는다. 그래서 저장 *전* 단계에 마스킹이 필요하다.

- **처리 시점**: `log_watcher.py`가 로그 라인을 읽어 `trigger_agent_pipeline`을
  호출하기 직전, 혹은 `learn_from_feedback`이 ChromaDB에 upsert하기 직전 —
  둘 중 어디서 마스킹하든 파이프라인이 실제로 진단·조치에 쓰는 텍스트가
  아니라 **저장용 사본**에만 적용해야 한다(마스킹이 진단 정확도를 떨어뜨리면
  안 됨. 예: IP를 통째로 지우면 "어느 서버 문제인지" 진단 근거가 사라짐 →
  마스킹은 어디까지나 export/누적용 사본에서만).
- **마스킹 대상 패턴(초안)**:
  - IP 주소 (IPv4/IPv6) → `<IP>`
  - 이메일 주소 → `<EMAIL>`
  - 파일 경로 내 사용자명 (`/home/<user>/`, `/Users/<user>/`, `C:\Users\<user>\`) → `<HOME>`
  - 호스트명/도메인 (사내 도메인 패턴) → `<HOST>`
  - API 키/토큰으로 보이는 문자열(긴 영숫자 조합, `.env` 키 패턴) → `<SECRET>`
- **검증 절차**: 마스킹 규칙을 코드화하면, 실제 축적 전에 표본(예: 온라인
  학습으로 이미 쌓인 기존 `learned_*` 엔트리 중 N건)에 적용해 마스킹 전/후를
  사람이 직접 대조 리뷰 — 정규식이 못 잡는 패턴이 있는지 확인한 뒤에만
  실제 파이프라인에 반영한다.

## 5. 보관 기간

- ChromaDB에 upsert된 (마스킹된) 학습용 데이터: 삭제 정책 없이 유지(현재
  L1 캐시 자체가 지속 학습 캐시라 이게 곧 "모델 상태"에 해당).
- raw 로그 원문(마스킹 이전 사본)은 축적 목적이 아니라 마스킹 검증용 임시
  자료이므로, 검증이 끝나면 별도 보관 기간을 두지 않고 폐기 — 구체적
  보관 일수는 실제 수집 협조자가 정해질 때 §3 동의 절차와 같이 확정한다.
