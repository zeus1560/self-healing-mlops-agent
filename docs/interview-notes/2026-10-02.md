## 1. 원 메모 (인터뷰 직후 작성, 무편집)

```
장애 대응은 대표님이 직접
밤에 콜을 받은 적은 있고 답답한 거는 클라이언트한테 혼나고 클라이언트는 화가 나고
어떤 장애가 나나 -> 기능이 장애가 난다 -> 원인 파악도 오래걸리는데 복구가 진짜 빨리 되야 한다 1시간 이상 걸리면 안됨
슬랙을 사용하신다 -> 아쉬움은 있다 슬랙에서 오는 에러 메세지는 순수 에러 로그 메시지라 파악하는데 시간이 걸린다
에러에 대한건 승인이 당연히 있어야 한다
학생이 만든다고 하면 당연히 안 쓴다 -> 효과만 좋으면 되는데 그걸 무언가 증명이 되야 한다
당연히 있다 -> 니즈가 무조건 있긴하다
사례가 더 중요 그 뒤 가격
개발 베이스이면 전자 다른 데서는 그럴수도 있다? 대표님이라면 오픈 소스로 하실 거 같다
```

## 2. 가설 판정

| 가설 | 판정 | 근거 |
|------|------|------|
| H1 원인 파악이 병목 | **부분적으로 맞음** | "원인 파악도 오래 걸리는데 복구가 진짜 빨리 돼야 한다, 1시간 이상 걸리면 안 됨" — 실제 기준은 장애~복구 전체 1시간. 원인 파악은 그 안의 큰 비중 |
| H2 승인은 당연히 필요 | **맞음** | "에러에 대한 건 승인이 당연히 있어야 한다" |
| H3 규제 클라이언트 니즈 | **판정 보류** | "니즈가 무조건 있긴 하다" — 직접 경험이 아닌 의견. 금융권 실무자 F의 직접 경험 기반 반대 의견과 충돌(§4) |

- 도입 결정 기준: **검증된 사례 > 가격**
- 오픈소스 vs 유료 지원: 개발 기반 조직이면 오픈소스, 다른 곳은 유료 가능. A 본인은 오픈소스.

## 3. 주요 발견

1. **신뢰의 문턱이 기능보다 앞선다.** "학생이 만든다고 하면 당연히 안 쓴다 —
   효과가 증명돼야 한다." 현재 증거는 테스트 환경 수치(end-to-end 34%)뿐이고
   실운영 사례는 0건이다.
2. **Slack의 원본 에러 로그 해석이 구체적 고통이다.** 이 프로젝트의 Slack
   승인 요청은 이미 진단 근거·설명을 포함한다(`src/slack_bot.py`) — 가장 직접
   맞닿는 지점.
3. **고통의 본질은 클라이언트 관계다.** "클라이언트한테 혼나고, 클라이언트는
   화가 나고" — 기술 지표(MTTR)보다 "클라이언트가 알기 전에 원인을 안다"는
   표현이 더 와닿을 가능성.

## 4. 이전 인터뷰(F, 금융권 서버/인프라 실무자)와의 충돌

F는 "실제 서비스에서는 기능이나 에러가 절대 발생하면 안 된다 → 그래서 이런
도구가 필요 없다"고 했고, 서버가 여러 대인데 어떻게 하는지 물었다.

| | A (클라이언트 수행 개발사) | F (금융권 운영) |
|---|---|---|
| 장애에 대한 전제 | 난다. 1시간 안에 복구해야 함 | 나면 안 된다 |
| 대응 방식 | 사후 대응(콜 받고 원인 파악) | 사전 예방(테스트·변경 통제·이중화) |
| 이 도구에 대한 반응 | 필요, 단 증명 필요 | 필요 없음 |

**해석(가설, 미검증)**: 영역 차이로 보는 게 자연스럽다. 금융권은 장애를
이중화·변경 통제·사전 테스트로 "막는" 구조라, 운영 중 장애를 진단·복구하는
도구가 끼어들 자리가 작다. A 같은 개발사는 장애가 실제로 나고 시간 압박 속에
사람이 직접 대응한다.

**함의**: 원페이저·competitive-research의 1순위 타깃인 "규제 산업"은 금융권
직접 경험자에게 부정당했다. 반면 A 유형(장애가 실제로 나고, 클라이언트 압박이
있고, 오픈소스 수용적)은 강한 신호를 줬다. 인터뷰 2건이라 결론은 이르지만,
**다음 인터뷰는 A 유형(개발사·중견 SaaS)을 늘려 확인**하는 것이 맞다.
