# self-healing-mlops-agent: 1페이지 요약

## 한 줄 소개
프로덕션 장애를 감지·진단하고, 복구 방안을 제안하되 **실행은 항상 사람의 승인을 거치는** 오픈소스·셀프호스팅 로그 이상 감지 에이전트입니다.

## 왜 "완전 자동 복구"가 아닌가
장애 복구를 시스템이 알아서 실행하는 방식은 책임 소재가 불분명해지는 순간 신뢰를 잃습니다. 저희는 이걸 실무자 피드백(금융/뱅킹 섹터)을 통해 직접 확인했고, 그래서 설계 원칙을 처음부터 "완전 자동화"가 아니라 **"자가 진단 + 인간 승인 기반 복구 제안"**으로 잡았습니다.

승인 게이트 자체는 이제 업계 표준입니다 — Datadog, New Relic 같은 도구들도 이미 실행 전 승인 단계를 지원합니다. 저희가 다른 지점은 **그 승인 화면에 뜨는 "근거"가 실제로 믿을 만한지를 직접 검증했다는 것**입니다. bias-injection과 counterfactual 테스트로 검토 단계가 "권위 주장·허위 성공이력·긴급성 압박" 같은 편향 문구에 흔들리지 않는지 확인했고, 별도로 근거 문구의 품질을 채점해 승인 근거는 막연한 반면 거부 근거는 구체적(PID 명시 등)이라는 비대칭을 발견해 공개했습니다(아직 표본이 작은 1차 측정입니다). 근거 문구를 만드는 것과, 그 근거가 실제로 믿을 만한지 적대적으로 검증하는 것은 다른 차원의 작업이라고 생각합니다.

## 검증 상태 — 데모용 숫자가 아닙니다
- 독립 벤치마크 스크립트 기준 핵심 지표 확보 (스크립트로 재현 가능)
- 사전 정의된 15종 장애 유형 **밖**의 시나리오 10건을 실제 VM(격리된 DB 사본)에서 추가 검증 — 고정 케이스에서만 잘 도는 시스템이 아닌지를 직접 확인
- 이 과정에서 실제 한계(임베딩 기반 라우팅의 오탐 사례)를 발견했고, 숨기지 않고 백로그로 문서화 — 저희는 완벽한 자동 판단을 주장하지 않습니다. 그래서 인간 승인이 장식이 아니라 실질적인 안전장치로 존재합니다.

## 누구에게 필요한가
저희 판단으로는 아래 두 그룹에 가장 잘 맞습니다.

- **규제 산업(금융/뱅킹 등) 엔터프라이즈**: 로그·운영 데이터가 제3자 SaaS로 나가는 것 자체가 컴플라이언스 문제가 되는 경우, 셀프호스팅은 "선호"가 아니라 "요건"입니다. 에이전트와 데이터 저장소는 전부 고객 서버 안에서 돌고, LLM 추론도 기본값인 로컬 모드(Ollama)에서는 서버 안에서 처리되어 LLM 분석용 데이터가 외부로 나가지 않습니다(2026-10-04 전환). 성능을 우선하는 회사는 외부 LLM API(Groq)를 쓰는 클라우드 모드를 명시적으로 켤 수 있고, 이 경우 로그 일부가 외부로 나갑니다. 단, 로컬 모델의 신규 에러 대응 품질은 낮아(대상 일치율 3.3%) 로컬 모드의 자동 복구는 사실상 L1 캐시와 사람 승인에 의존합니다.
- **전담 SRE 팀을 보유한 중견 SaaS**: 종합 관측 플랫폼의 전체 비용을 다 내지 않고, 로그 이상 감지·복구 제안 영역만 오픈소스로 가져가고 싶은 팀.
